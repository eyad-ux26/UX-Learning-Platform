# Learner app: developer guide

How the learner app and the public site in `apps/web` are put together, and where to make a change. The admin panel
(`app/admin`, `components/admin`, `lib/admin`) has its own docs in `docs/admin/`. For the big picture (services, data
model, costs) see [architecture.md](architecture.md) and [data-model.md](data-model.md).

## Run it

```bash
npm ci
npm run tokens            # design tokens → packages/tokens/dist (CI checks it is up to date)
npm run dev               # Next.js dev server on :3000, copies lesson files first
```

Without Supabase variables the app runs on built-in fixtures for the screens that support them
(`UG_DEV_FIXTURE=1`, used by the browser checks in CI). For a real database copy the variable names from
`docs/billing-keys.md` and `docs/deploy-cloudflare.md` into `apps/web/.env.local`.

Checks, the same as CI (`.github/workflows/ci.yml`):

```bash
npm run validate          # content YAML
npm run typecheck
npm run lint              # ESLint + scripts/lint-logical.mjs (logical CSS only, for Arabic RTL)
npm test                  # Vitest in every workspace
npm run build
```

## The workspace

| Folder | What it is |
| --- | --- |
| `apps/web` | The Next.js 15 app (App Router, React 19, TypeScript strict), deployed to Cloudflare Workers with OpenNext |
| `packages/player` | The lesson player: the step state machine (`src/engine.ts`, pure) and its React UI (`src/ui/`) |
| `packages/content` | Loads, validates and compiles `content/paths/**.yaml` into `dist/` (generated, never edit by hand) |
| `packages/tokens` | Design tokens → CSS variables (generated `dist/`) |
| `supabase` | SQL migrations, RLS, seed scripts. `supabase/seed/` is generated from the content bundle |
| `content/paths` | Course content, see `docs/content-format.md` |
| `preview` | The standalone review player used in content PRs |

### Where code goes

- **Pure rule or calculation** (no I/O): `lib/<topic>.ts` with `lib/<topic>.test.ts`. Pages, jobs and tests then agree.
  Most of the app follows this, for example `lib/skill-state.ts`, `lib/freeze.ts`, `lib/billing/subscription.ts`.
- **Database or network on the server**: `lib/server/…`, starting with `import "server-only"`.
- **A screen**: the route's `page.tsx` loads data on the server and renders a view component from `components/<area>/`.
  Keep pages thin; put the markup in the component.
- **A mutation from a screen**: a server action (`actions.ts` next to the page) or a route in `app/api/`. Both check the
  signed-in user themselves; the middleware never decides access.

## Data and access

There are three Supabase clients in `lib/supabase/`:

| Client | Use | Sees |
| --- | --- | --- |
| `createClient()` in `server.ts` | pages, server actions, API routes | only the learner's own rows (RLS) |
| `createAdminClient()` in `admin.ts` | webhooks, cron jobs, writes after the route checked the user | everything (service role); server only |
| `createServerClient` in `middleware.ts` | refreshing the session cookie | nothing else |

Prefer the learner's own client. Use the admin client only after the code has checked who the user is.

The signed-in learner's state is one database call (`my_learner_state`, `lib/server/learner-state.ts`). Every
Supabase call is counted and timed per request (`lib/server/db-trace.ts`) and shows in the `Server-Timing` header.

## How a lesson works

1. **Content**: `packages/content` compiles the YAML into one JSON file per lesson. `scripts/copy-content.mjs` copies
   them to `public/c/` before every build. They are never public: the middleware and the Worker return 404 for them
   (`lib/private-content.ts`), and `lib/server/content.ts` reads them through the Worker's `ASSETS` binding.
2. **Page**: `app/[locale]/app/lesson/[lessonId]/page.tsx` loads the lesson and the learner, then renders `LessonRunner`.
3. **Playing**: `LessonRunner` wraps `LessonPlayer` from `packages/player`. Each answer is written to IndexedDB first
   (`lib/attempts.ts`, `lib/idb.ts`), so nothing is lost offline.
4. **Sync**: `lib/sync.ts` sends queued answers to `POST /api/attempts`, with retries.
5. **Scoring**: `lib/server/process-attempts.ts` decides the score on the server (the browser only says what the
   learner did), then updates skill states (`lib/skill-state.ts`), XP, streak and review queue.

The mastery round (`lib/mastery.ts`) and spaced review (`lib/review.ts`) reuse the same player with a cut-down bank.

## Strings (English and Arabic)

All UI text lives in `messages/en/` and `messages/ar/`, one JSON file per area (`app`, `account`, `public`,
`emails`, `billing`). `messages/index.ts` puts them together and says what each file holds; `i18n/request.ts` hands
them to next-intl. Every namespace lives in one file only, so a new string goes in the file that already holds its
namespace. `tests/messages.test.ts` fails when a key exists in one language only or a namespace is in two files.

Write both languages in the same change. Arabic is the default locale and the page is RTL, so CSS uses logical
properties only (`margin-inline-start`, not `margin-left`); `npm run lint` enforces it.

## Styling

Plain CSS in `app/styles/`, one file per area, on top of the design tokens (`packages/tokens`). Class names follow the
approved design canvas. Icons are Phosphor, built into CSS by `scripts/build-assets.mjs` and
`scripts/build-billing-icons.mjs`. Every screen supports light and night themes (`lib/theme.ts`, `components/ThemeSync.tsx`).

## Settings and switches

- **Worker variables** (`wrangler.jsonc` `vars`, secrets with `wrangler secret put`): see `docs/billing-keys.md`.
  Never commit a secret.
- **Panel flags** (`lib/app-config.ts`): read from the database at most once a minute; a database problem leaves
  every flag off.
- **Coming Soon gate** (`lib/coming-soon.ts`, `lib/team-access.ts`) and **maintenance mode** run in `middleware.ts`.

## Background jobs

`cf-worker.ts` runs the Cron Triggers in `wrangler.jsonc` and calls the routes in `app/api/cron/` with `CRON_SECRET`:

| Trigger | Routes |
| --- | --- |
| 02:00 UTC daily | `daily` (streaks, freezes, waitlist and trial emails), then `review-due`, then `billing` (renewals, retries) |
| every 15 minutes | `reminders` (daily reminders, removal of deleted accounts) and `admin` |

Each route answers with a summary and `more: true` while work is left; the Worker calls it again a few times.

## Tests

- Unit tests: Vitest, next to the file they test (`foo.ts` → `foo.test.ts`). Pure modules are tested directly;
  server modules are tested with fakes (for example `lib/billing/memory-store.ts` stands in for the billing tables).
- Browser checks in CI (`scripts/a11y.mjs`, `keyboard.mjs`, `flow.mjs`, `theme.mjs`) run against `next start` with
  `UG_DEV_FIXTURE=1`.
- `scripts/check-static.mjs` fails the build if Pro lesson content reaches a public file.

## Conventions

- TypeScript strict; the `@/` import alias points at `apps/web/`.
- Comments say why, not what. Many comments name the issue, migration or design frame a rule comes from (for example
  `#184`, `0039`, `canvas v63`); keep those references, they are how to find the decision.
- A database change is a new numbered file in `supabase/migrations/`; never edit one that has run.
- Content changes need the compiled bundle and the regenerated seed in the same PR (`npm run build -w @uxgate/content`,
  `npm run seed:sql`).
